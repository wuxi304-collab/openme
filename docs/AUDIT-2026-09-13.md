## 二、发现的问题与处理

### P1（高）`.ts` 扩展名冲突：TypeScript 文件被当成视频打开

**问题**：`.ts` 在注册中心被登记两次——MPEG Transport Stream（`video`，formats.ts）与 TypeScript（`code`）。`dedupeByExtension` 保留先出现的一项，因此：

```
.ts  →  category = "video"  →  ViewerRouter  →  MediaViewer
```

即 **TypeScript 源码会被送进媒体播放器**，而不是代码编辑器。对一个以“文件工作台”为定位、且内置 Monaco 编辑器的产品，这是直接可见的功能错误。

**根因**：`dedupeByExtension` 静默丢弃后出现的条目，且注册中心的重复检测测试只检查已经去重过的数组。

**修复**：

1. 移除 formats.ts 中冗余的 video `.ts` 条目（`.m2ts` / `.mts` 已在 expanded-formats.ts 覆盖摄像机与广播传输流），并保留说明性注释。
2. `dedupeByExtension` 改为显式冲突裁决：同一扩展名下**文本/代码类别优先于二进制/媒体类别**，避免未来再次静默覆盖。
3. 新增针对性回归测试。

### P2（中）注册中心重复检测是同义反复

**问题**：`registryCoverage.test.ts` 的 “has no duplicate extensions” 检查的是 `FILE_FORMATS`——即**已经去重之后**的数组。这项断言恒为真，因此完全无法发现源数组里的重复，正是 P1 长期存在的原因。

**修复**：新增基于 `BASE_FILE_FORMATS + EXPANDED_FILE_FORMATS` 源数组的重复检测；补充 `.ts` → TypeScript/code、`.m2ts`/`.mts` → video 的显式断言；并直接对冲突裁决函数做单元测试（两个方向都验证）。

### P2（中）自定义协议 `openme-media://` 可读取任意本地文件

**问题**：协议处理器直接把查询参数里的路径交给 `net.fetch`，没有类型限制：

```js
const mediaPath = new URL(request.url).searchParams.get("path");
if (!mediaPath || !fs.existsSync(mediaPath) ...) return 404;
return net.fetch(pathToFileURL(mediaPath).toString());
```

任何能被塞进该 scheme 的路径都会被读取为媒体流。

**修复**：新增 `isServableMediaPath()`：限定音视频扩展名白名单（已与注册中心全部 34 个 audio/video 扩展名逐项比对，无遗漏）+ `path.resolve` 归一化 + 真实文件校验。IPC `get-media-url` 同步复用该校验。已补回遗漏的 `.ape`。

### P2（中）行尾符号导致整文件 diff 噪声

**问题**：本次编辑工具按 Windows 平台习惯写出 CRLF，而仓库原本统一为 LF，导致 `README.md`、`electron/main.js`、`App.tsx`、注册中心等文件在 git 里显示为**整个文件被重写**（数千行噪声），真实改动被完全淹没。

**修复**：将该批文件归一化回 LF；新增 `.gitattributes`（`* text=auto eol=lf`，`.cmd/.bat` 保持 CRLF，二进制资产标记 `binary`）从机制上防止复发。

## 三、已核实但**不是**问题（避免误报）

这几项在审计中一度怀疑有问题，经实测排除，特此记录以免后续重复排查。

- **CSP `frame-src 'none'` 会不会阻断 Markdown / DOCX 预览？**
  不会。用 Electron 34 搭了对照实验（含正向对照以确认 CSP 确实生效）：`about:srcdoc` 属于继承父文档 CSP 的本地 scheme，**不受 `frame-src` 约束**，`sandbox=""` 的 iframe 正常渲染。Markdown 预览与 Word 预览功能正常。
  （附注：实验初期判定的“被阻断”是误判——`sandbox=""` 会赋予 iframe 不透明源，父文档本就无法访问其 `contentDocument`，与 CSP 无关。）

- **生产环境（`file://` 加载）CSP 是否生效？**
  生效。`webRequest.onHeadersReceived` 对 `file://` 请求同样会触发，正向对照中内联脚本被成功拦截。

- **ZIP 解压路径穿越（Zip Slip）**
  防护正确：逐项 `path.posix.normalize`、拒绝 `../` 与绝对路径、并对最终目标路径做 `startsWith(destinationRoot + sep)` 校验，另有 2 GB / 100,000 项上限。

## 四、`package-lock.json` 专项：1.9 万行改动的真实成因

这是本次审计中最容易被误判的一项，已彻底查清：

| 指标 | 结果 |
| --- | --- |
| 依赖版本变化 | **0** |
| 被移除的包 | **0** |
| 新增的包 | **80 个**，全部为 `dev` / `devOptional` |
| 生产依赖版本一致性 | 16 个生产依赖版本**逐一比对，完全一致** |
| 新增包来源 | vitest 2.1.9 的依赖树（`@vitest/*`、`chai`、`tinypool`、`tinyrainbow` 等）+ 约 40 个平台专属 esbuild 可选二进制 |

**结论：仓库里已提交的 lockfile 完全没有 vitest 条目**（`git show HEAD:package-lock.json` 中 `"node_modules/vitest"` 出现 0 次），而 `package.json` 声明了 `vitest ^2.1.9`。也就是说**已提交的 lockfile 与 package.json 不同步**——当前工作区的 lockfile 才是补全后的正确版本。

由此推出一个关键且反直觉的结论：

> **现在如果把 CI 的 `npm install` 改成 `npm ci`，CI 会直接失败**（`npm ci` 要求 lock 与 package.json 严格同步）。CI 之所以一直正常，正是因为用的是 `npm install`——它会自动补齐缺失依赖，也正是这 1.9 万行 diff 的来源。

因此**正确顺序是**：先提交更新后的 lockfile，**之后**再把 CI 切到 `npm ci`。顺序颠倒会直接打断构建。

另一个可选项：新增的 80 个包中有 81 条 `resolved` 指向 `registry.npmmirror.com`（`.npmrc` 配置了镜像）。功能上无碍，但对于公开仓库，若希望 lockfile 统一指向 `registry.npmjs.org`，可在网络条件允许时执行 `npm install --package-lock-only --registry=https://registry.npmjs.org` 重新生成。本次未执行（涉及整表重写且依赖外网连通性）。

## 五、其余待决策项

1. **CI 加固（须等 lockfile 提交后再做）**：`.github/workflows/build.yml` 用 `npm install`、`npm audit --omit=dev` 又是 `continue-on-error: true`，已知高危依赖不会让构建失败。建议先提交 lockfile，再切 `npm ci` 并让审计结果可见。
2. **主进程 `detectFileType()` 是一张过时的小映射表**，与注册中心并存且结果被渲染进程覆盖，属于冗余逻辑，建议后续收敛到注册中心单一来源。
3. **打包体积漂移**：AGENTS.md 记录首页 JS 约 229 KB（gzip 约 72 KB），实测 `index` chunk 为 323 KB（gzip 89 KB）。不属于缺陷，但建议更新记录或设立体积预算。
